# CARRY.md — quickserve-ai/gascity carry model (one fleet build)

This file records what is specific to this fork: the one build it runs, its branches, the
behaviors it carries above upstream main, the beads pin, and how the carry is re-synced and
landed. The gas-city-carry skill governs procedure. Git governs state: when this file and Git
disagree, Git wins.

The ledger, dropped and count sections are generated by `gen_carry_md.py` in resync-tools, from
the re-sync's decisions and its linearize report. To change a row, change its inputs and
regenerate; do not edit the tables by hand.

## The ledger

Every kept row is an intentional divergence from upstream main. A re-sync that loses one silently
is a regression. "Drop when" is the absorption test: before dropping a row, prove it by patch-id or
range-diff and by the named behavior check on upstream.

Commit cells name commits on `carry/operational` after the 2026-09-28 re-sync (re-sync #4, base `458de7a81`). "(replayed)" marks a
commit taken from an upstream PR branch; it drops by patch-id when that PR merges. "folded into"
names the later commits that carry a row whose own re-expressed commit went empty at linearize;
"(integration)" marks the integration commit. A commit added after integration carries its note in
parentheses. The commit that adds this file sits on top of the stack and is not listed.

the highest Dolt schema a `gc` binary can open. Since the 2026-09-15 re-sync (and still at the 2026-09-28 one), `go.mod` takes upstream
main's beads requirement unmodified, and adds one replace so the code gc links is the fleet

`checkVersionCompat` (`internal/beads/contract/preflight_checker.go`) refuses the native store on a
confirmed mismatch between `bd`'s version and the beads version `gc` links. It passes an equal
version, a newer `bd` of the same major version, two prereleases of one release, and a linked
library it cannot confirm (a pseudo-version, a replaced module or a source build). The fleet rule
is stricter than the check: `bd`'s `main.Version` equals the beads version the unit links, so every
machine's `bd` moves with the unit.

The fleet beads fork (lyft; be-oau) is re-synced to v1.3.0 as the carry-v66-1.3.0 lineage (rc.2 before
this re-sync), and its released fleet tag is what the replace names. Because the linked library is then a REPLACED module,
`checkVersionCompat` reports it unconfirmable and passes for any `bd` with a readable context — the
label stops being a gate and stays a fleet rule, enforced by the unit's own preflight rather than by
gc. `make check-gomod-replace`, a CI step, still refuses a replace that names a pseudo-version, a
bare prerelease, a local path or a git ref; its one admission is the fork path at
`vX.Y.Z[-rc.N]-fleet.<YYYYMMDD>[.<serial>]`, with fixtures.

**Moving the pin moves the fleet.** A shared store's writers move in one window: a binary that
migrates a database past what another machine's `bd` knows produces schema skew from the other
side. On this carry, a store newer than the binary holds session reconciliation and reloads (the
schema-skew row) instead of falling back silently to the exec store.

## Deploy recipe

Fleet machines do not build `gc`. A unit is an annotated `fleet/YYYY-MM-DD` tag on
`carry/operational`. Pushing the tag runs `.github/workflows/fleet-release.yml`, which builds
linux-amd64 and darwin-arm64 from a fresh checkout with `-tags gms_pure_go` and publishes the
release that is the unit's attestation. Each machine installs the unit per qc-bridge
`shared/fleet-gc-binary-roll.v1.md`: the order, preconditions, swap, countersign and rollback live
there, not here.

Fork-specific notes that still hold:

- On macOS, `gc supervisor install` is the refresh step because of the launchd refresh row: it
  re-registers the job, polls until the new build serves, and rolls back otherwise. Upstream's
  install returns early when the plist is unchanged, so an upstream binary does not refresh after
  an in-place swap. Never refresh with a bare `launchctl kickstart -k` (ga-4v3ckk).
- On macOS, `gc start` refreshes, and so restarts, a live launchd supervisor. Both laptops already
  run this behavior.
- The deploy-freeze marker `~/.gc/deploy-freeze.json` blocks `gc supervisor install` and
  `make install`. A release consume runs no `make`, so the roll page's preconditions read the
  marker by hand.
- `make install` swaps by atomic rename, verifies the installed binary without a pipe, and keeps
  two backups. It serves development builds; a fleet machine installs the attested asset byte for
  byte.
- At each city's next bd/core pack re-pin, a city that relied on pushing every Dolt remote sets
  `GC_DOLT_REMOTE_<DB>=a,b` on the dolt-remotes-patrol order env (the gc dolt sync row). Without it,
  extra mirrors stop receiving pushes, and health flags them.
- The release workflow warms modules against a scratch modfile (formerly fork PR #62), so a
  tag-push build no longer stamps `-dirty`; still check the first unit for `-dirty` before
  countersigning.

## Rebase cadence

Overseer rule, 2026-09-15: `carry/operational` is re-synced onto upstream main at least every
seven days. The clock is the carry's merge base with upstream main. Once that base is seven days
old, everything else waits until the re-sync lands: no upstream PRs, fork picks, reviews or
investigations. This stack's base is 2026-09-28 (`458de7a81`); re-sync #4 is prepared (landing time to be filled at the landing), and the next re-sync is due by 2026-10-05 (placeholder: landing + 7 days).

Check the clock at every boot and before any fork or upstream work:

```sh
git fetch upstream && git fetch origin carry/operational
git log -1 --format=%cd --date=short "$(git merge-base upstream/main origin/carry/operational)"
```

A re-sync is all of these:

1. Refresh the fork's `main` from `upstream/main`.
2. Rebase `carry/operational` onto it.
3. Write a drop-or-carry decision for every ledger row.
4. Get `CI / required` green on the exact SHA.
5. Cut the fleet unit from the result.

A partner town's constraint is not a reason to wait: if one town's host cannot run the re-sync,
the other town runs it and the first reviews. Tell the other fork owner before touching the shared
carry.

The re-sync pipeline, in resync-tools (gc-iexd):

1. Classify: reviewer lanes place every carry commit into a behavior with a verdict and evidence,
   and `verdicts.py` merges them into `state/clusters.json`.
2. Fold: `fold2.py` folds the carry's history into one commit per behavior segment on the old base,
   tree-equal to the old tip.
3. M1: a rebase that drops the DROP segments (`seqedit.py`, `m1-plan.json`) leaves the kept stack on
   the old base. Every commit carries `Folded behavior:` and the original SHAs.
4. Merge: rows with an upstream PR are replayed from their PR branches onto upstream main, then M1
   is merged and resolved once per file. Owner decisions go to `decision-notes.md` and the
   overrides file.
5. Linearize: `linearize.py` re-expresses M1 as per-behavior commits on the new base, ending at the
   resolved tree, plus one integration commit.
6. Ledger: `gen_carry_md.py` writes this file from the decisions, the replay map, the row text and
   the linearize report.
